# Software Design

## Scope

`bidmart-frontend` is the BidMart single-page application for buyer, seller, and admin workflows:

- Authentication, registration, profile, 2FA, and admin user management.
- Marketplace catalogue browsing, search/filter, listing detail, and seller listing management.
- Auction bidding, proxy bid entry, realtime auction updates, and win-to-order continuation.
- Wallet balance, top-up, withdrawal, payment status, and transaction history.
- Orders, shipping status, dispute creation, dispute resolution visibility, and notifications.

Server-side business rules remain in backend services. The frontend consumes the API gateway contract and presents the workflows.

## Module Structure

| Module | Path | Responsibility |
|--------|------|----------------|
| Auth | `src/modules/auth/` | Login, register, 2FA, admin, profile |
| Catalogue | `src/modules/catalogue/` | Marketplace, seller studio, listing detail |
| Auction | `src/modules/auction/` | Realtime bidding patches and bid UI helpers |
| Wallet | `src/modules/wallet/` | Balance, top-up, payment detail, withdrawal |
| Orders | `src/modules/orders/` | Order list, detail, timeline, dispute actions |
| Notifications | `src/modules/notifications/` | Notification center and realtime subscriptions |
| Home/Layout | `src/modules/home/`, `src/layout/` | Marketplace entrypoint, navbar, route shell |

## SOLID Mapping

| Principle | Implementation |
|-----------|----------------|
| SRP | Pages orchestrate workflows; API adapters, reusable UI, route shell, and context providers are separated. |
| OCP | New pages are registered through `AppRoutes`; new UI cards/hooks can be added without changing backend adapters. |
| LSP | Role-aware route wrappers and shared layout components behave consistently for buyer, seller, and admin roles. |
| ISP | Hooks expose narrow contracts, such as `useNotificationsWebSocket`, `useWalletData`, and route-level module APIs. |
| DIP | Components depend on context/API abstractions rather than direct `localStorage`, service hostnames, or backend internals. |

## Design Patterns

| Pattern | Mapping |
|---------|---------|
| Container/presentational components | Page components coordinate state while reusable components render cards, panels, nav, and status blocks. |
| Custom hook facade | Hooks hide async state, realtime subscriptions, and API calls behind small interfaces. |
| Context provider | `AuthContext`, `WalletUIContext`, `ToastContext`, and notification websocket context avoid prop drilling. |
| Adapter | API utilities map UI requests to gateway endpoints and normalize DTO handling. |
| Strategy-like render states | Loading, error, empty, and content states are consistently represented across home, catalogue, wallet, and orders. |
| Route-level lazy loading | Heavy pages are split with `React.lazy` in `src/layout/AppRoutes.tsx`. |

## UX Design Direction

- `/` is a usable marketplace home, not a marketing-only landing page.
- The hero uses real marketplace imagery, accessible carousel controls, pause-on-hover/focus, and reduced-motion behavior.
- Marketplace, listing detail, wallet, and order pages prioritize action clarity: search/filter, sticky bidding actions, wallet feedback, and order timeline/status.
- UI tokens favor a clean marketplace palette with visible focus rings, stable touch targets, loading skeletons, and explicit empty/error states.

## Realtime Design

- STOMP/SockJS subscriptions are shared through hooks and context.
- Guest home does not load websocket libraries; authenticated contexts lazy-load STOMP only when a connection key exists.
- Public auction updates patch React Query cache; private notification destinations are user scoped.
